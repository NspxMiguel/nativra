Two goals, worked in order:

1. **32-bit (x86) games** — a WoW64-style x86-to-x64 translation layer so PE32

## Goal 1 — x86 layer

### Done

**Portable core (`x86/Nativra.X86`, netstandard2.0).** Referenced by the UWP
app; unit-tested on net8.0 on the runner and locally.

- `Cpu/Decoder.cs` — instruction length + operand decoder for the one-byte,
  `0F`, `0F38`/`0F3A` and x87 maps, with VEX length skipping. Getting length
  exact is what lets the JIT step over instructions it does not translate.
- `Cpu/Interpreter*.cs` — a reference interpreter: integer ALU, shifts/rotates,
  mul/div/imul, BCD, string ops (`rep` forms), and the two-byte map
  (setcc/cmovcc, bit ops, movzx/movsx, shld/shrd, cmpxchg, xadd, bswap, …).
- `Cpu/Fpu.X87.cs`, `Cpu/Fpu.Sse.cs` — the x87 stack (80-bit registers kept in
  FXSAVE layout), MMX, and SSE/SSE2. CPUID advertises only what the interpreter
  actually executes (up to SSE2).
- `Cpu/GuestMemory.cs` — a 4 GB paged guest address space with two backings: a
  managed one for the interpreter and the tests (any OS), and a native 4 GB
  reservation where guest address + host base = host pointer, which the JIT
  addresses directly.

**Differential test against real silicon.** `x86/harness/oracle.c` is a 32-bit
program that, for each snippet in `snippets.txt`, builds random guest states,
runs the snippet natively (under WoW64 on the runner), and prints the state
before and after — registers, EFLAGS, the full FXSAVE image, and the touched
data and stack. `InterpreterOracleTests` replays each input through the
interpreter and checks it reaches the same state. **132 snippets pass
bit-for-bit**, covering every category above. The only masked fields are the
sticky FP exception-status bits (FSW/MXCSR), which no software interpreter
reproduces and no correct guest depends on; the JIT, running on real silicon,
reproduces them exactly.

**CI.** `.github/workflows/x86-harness.yml` (windows-latest) builds the oracle
with MSVC's x86 toolchain, regenerates the vectors on the runner's own
processor, and runs the suite. Independent of `build-uwp.yml`.

**x86-to-x64 block JIT (`x86/Nativra.X86/Jit`).** Translates a run of
straight-line guest code into one self-contained x64 function and caches it by
guest EIP.

- Guest GPRs are pinned to host GPRs (`Ctx.GuestToHost`), so a guest ALU
  instruction becomes the identical x64 instruction on the mapped registers and
  its EFLAGS come straight from the host processor — no flag recomputation, and
  a natural bit-for-bit match with real silicon.
- Guest memory is addressed as `host_base + guest_address` (the native 4 GB
  reservation), the standard box64/blink trick, so a load is one `lea` for the
  address and one `mov` through the base register.
- `CodeCache` publishes each block into its own page, committed RW, filled, then
  flipped to RX — the console's W^X route (RWX up front is refused; JitProbe
  measured this).
- The engine is JIT-first with an interpreter fallback: a block ends at the
  first control-flow or untranslated instruction and the reference interpreter
  runs that one, so the JIT is only ever faster, never a second source of truth
  that could diverge.
- Covered inline: the ALU set (reg/reg, reg/mem, mem/reg, immediates), mov in
  every form, lea, test, inc/dec/neg/not, shifts/rotates by imm/1/CL, mul/imul/
  div/idiv, imul 2- and 3-operand, movzx/movsx, setcc, cmovcc, bswap, push/pop.
- The **same hardware oracle** validates the JIT: every case runs through the
  compiled code and is compared to real silicon with **no flag mask at all**
  (the flags are the host CPU's own). 308 differential checks pass, plus
  end-to-end engine tests (a summation loop, an array walk through guest memory,
  a call/ret across the guest stack, block-cache reuse).

**PE32 loader (`Loader/Pe32Image.cs`).** Maps a 32-bit image into the *guest*
space — not into the host process, which is what the 64-bit `PeImage` does and
what a PE32 cannot use: sections at their RVAs, HIGHLOW base relocation when the
preferred base is taken, the export table, the TLS directory, and import binding
by name and ordinal through a pluggable binder. Tested with a PE32 assembled
byte-for-byte in the tests (`TestPe32`), so no toolchain is involved.

**Guest process (`Loader/GuestProcess.cs`, `GuestImports.cs`).** What turns the
primitives into something that can start a program:
- a 1 MB stack, a 32-bit TEB (FS base, self pointer at `fs:[18h]`, PEB at
  `fs:[30h]`, stack bounds, SEH chain end, last-error slot, TLS slots) and a PEB
  (image base, OS version, processor count, not-being-debugged);
- **imports trap into host code**: each unserved import is bound to a unique
  sentinel address in an unmapped strip; the run loop checks EIP against the
  sentinels before every block, so a guest `call [iat]` lands in a host
  handler, which reads its arguments off the guest stack and returns EAX:EDX.
  The handler declares its convention, so the loop pops the right number of
  bytes — **stdcall and thiscall pop, cdecl does not** — and the tests prove it
  by running forwarders that crash on the wrong cleanup, under both the
  interpreter and the JIT;
- **a game's own DLLs link into the guest**: when an import names a DLL the
  game carries, the host hands over its bytes, it is mapped (relocated if need
  be) and the import binds to its real export; anything else falls back to a
  sentinel. Asked once per module. `DllMain(PROCESS_ATTACH)` runs in load order;
- runs stop cleanly on return, `ExitProcess`, a guest fault, a missing import
  (named), or a block budget; if the host refuses to publish JIT code mid-run
  the loop carries on in the interpreter from the same state.

**Baseline kernel32 (`Loader/GuestKernel.cs`, `GuestHeap.cs`).** Pure guest-memory
implementations of what a program's startup reaches for first: a first-fit heap
(`HeapAlloc`/`Free`/`ReAlloc`/`Size`, zeroing), `VirtualAlloc`/`Protect`, TLS,
last error, `GetModuleHandle`/`LoadLibrary`/`GetProcAddress`/`FreeLibrary`/
`GetModuleFileName` (game DLLs map on demand and run `DllMain`; system DLLs get a
stand-in handle and `GetProcAddress` hands out only what the host serves — a
probe for an optional API such as `FlsAlloc` is told it does not exist, so the
program takes its fallback, and the name is recorded), command line, timing,
`GetSystemInfo`, `ExitProcess`, and critical sections as no-ops.

**Wired into the app (`uwp/Kiosk/Native/X86Launch.cs`).** `NativeProbe` used to
refuse any executable that was not AMD64 PE32+. It now routes i386 PE32 to
`X86Launch`: guest memory and JIT code pages through `VirtualAllocFromApp`/
`VirtualProtectFromApp` (the app-container allocators; the package already
declares `codeGeneration`), game DLLs read through `FileWatch` (so a game on a
USB drive works), then `DllMain`s, then the program's entry point. The x86 core
is referenced as a project (`Kiosk.csproj`, `Kiosk.sln`).

**C runtime surface (`GuestKernel.Runtime.cs`, `GuestKernel.Files.cs`).**
Everything the MSVC runtime (static `/MT`, or `ucrtbase`/`vcruntime140`/
`msvcp140`) calls in start-up and ordinary use: pointer encoding, SList,
start-up info, environment, standard handles (writes go to the probe log as
`x86.log=`), code page 1252 and UTF-8 conversion, en-US locale queries,
`LCMapString`/`CompareString`/`GetStringType`, version, real-time clocks,
memory status, `Global`/`Local` allocators, FLS, `InitOnce`, SRW locks and
condition variables, events and waits (single thread), `lstr*`,
`OutputDebugString`, winmm `timeGetTime`. API-set names (`api-ms-win-core-*`,
`kernelbase`) fold onto kernel32 and `api-ms-win-crt-*` onto ucrtbase.
Files go through `IGuestFiles` (System.IO by default): `CreateFile`, reads,
writes, seeking, sizes, attributes, `FindFirstFile` with DOS wildcards, the
current directory, `GetFullPathName`; every file a game looked for and did not
find is reported as `x86.files-not-found=`.

**SEH (`GuestKernel.Seh.cs`).** `RaiseException` walks the guest's `FS:[0]`
chain and `RtlUnwind` unwinds it, as a state machine in the run loop: a handler
is entered with a sentinel as its return address, so one that catches (C++
`catch`, `__except`) and never returns just abandons its dispatch. An exception
nobody handles stops the run as `raised exception 0x…`.

**Packaged 32-bit DLLs.** `build-uwp` builds the 32-bit shims into
`uwp\Redist\x86` and copies the redistributable x86 VC runtime
(`vcruntime140`, `msvcp140`, …) and `ucrtbase` beside them; they ship as `x86\`
in the package. A module the game does not carry comes from there
(`x86.packaged=` lists which).

**End-to-end test with real programs.** The harness job compiles
`x86/harness/guests/crt_test.cpp` with MSVC twice (`/MT` and `/MD`), checks both
exit 42 on real hardware, then runs both through the layer
(`GuestProgramTests`): C runtime start-up and exit, containers, a C++ throw
through three frames with destructors, `__try/__except`, `fopen`/`fprintf`/
`fscanf`, `printf("%.4f")`. The `/MD` build maps the runner's own 32-bit
`ucrtbase`, `vcruntime140` and `msvcp140` into the guest.

### To measure on the console

Launch **WAVESHAPER** (Steam 562260, 32-bit only). For now the home screen
still shows the "architecture not supported" message when it stops — that is
expected. Then fetch two files from the app's LocalState folder:

1. `native-probe.txt`, the `x86.*` lines:
   - `x86.failed=…` — present only if the layer could not start at all. The
     likeliest cause is the 4 GB guest reservation being refused by
     `VirtualAllocFromApp`; note the error text.
   - `x86.image=` — did the program map, and at its preferred base?
   - `x86.jit=on` means guest pages and executable JIT pages both worked on the
     console. `x86.jit.refused=` means executable pages were refused mid-run
     (the run continued in the interpreter).
   - `x86.init=` / `x86.run=` — **the key line**: `missing import X` names the
     next handler to write; `fault at 0x…` is a guest crash (send the
     `x86.eip=` line with it); `raised exception 0x…` is an exception the game
     did not handle (0xE06D7363 is a C++ throw); `exited with code N` means the
     program ran to its own end.
   - `x86.packaged=` — which DLLs came from the package's `x86\` folder;
     `x86.files-not-found=` — files the game looked for and did not get (a
     path mapping problem shows up here first); `x86.log=` — the game's own
     debug output and stdout; `x86.recent=` — the last 24 imports called,
     oldest first: where a run that stopped or stalled was.
   - `x86.blocks=` and `x86.seconds=` — blocks per second, the first
     performance baseline for the JIT on the console's CPU.
   - `x86.imports.<dll>=N (M served)` and `x86.probed-absent=` — the import
     surface still to cover.
2. `x86-imports.txt` — every import of every mapped module, marked `linked`
   (to a game DLL), `served`, or `MISSING`. Send it back whole: it sets the
   order of the next handlers.
3. A/B: create an empty `x86interp.txt` in LocalState and launch again. The
   run then uses only the reference interpreter. If the `x86.run=` line differs
   from the JIT run, the JIT has a bug the runner's differential tests missed —
   report both lines.

## Goal 2 — D3D9 on D3D11

`native/directx-redist/d3d9/`, built as `d3d9.dll` by the redist workflow and
packaged with the other shims (`build-app.cmd` → `uwp\Redist`).

### Done

**Shader translation (`dxso.cpp`).** D3D9 bytecode (vs_1_1 … vs_3_0,
ps_2_0 … ps_3_0) becomes SM5 HLSL, compiled by the d3dcompiler_47 the package
already carries — the one compiler that has to be right about DXBC is
Microsoft's. The whole D3D9 instruction set of those models is covered: ALU and
matrix macros, the scalar ops with D3D9's own edge rules (`rsq`/`log` of `|x|`,
`pow` of `|x|`), texture ops (`texld`/`texldp`/`texldb`/`texldl`/`texldd`,
`texkill`), predication (`setp`, per-component predicated writes), flow control
(`if`/`ifc`/`else`, `rep`, `loop` with `aL`, `break*`, `call`/`callnz`/`ret` as
HLSL functions), relative addressing through `a0`/`aL`, `def`/`defi`/`defb`,
`vPos`/`vFace`. Varyings travel in fixed slots declared in full in both stages,
so any vertex shader links with any pixel shader under D3D11's register rules;
integer vertex formats (UBYTE4, SHORT2/4) get a shader variant that fetches
integers.

**The device (`d3d9_*.cpp`).** `IDirect3D9Ex` and `IDirect3DDevice9Ex` over
D3D11: 2D and cube textures, render targets, depth-stencil surfaces, vertex and
index buffers (lockable through CPU shadows, with format conversion for
L8/A8L8/X8/R8G8B8…), vertex declarations and FVFs, programmable draws, every
primitive type (fans expanded to lists), the user-pointer draws, instancing
through stream frequencies, render states cached as D3D11 state objects,
samplers (filtering, addressing, LOD, border, sRGB), clears (rectangles, via
`ClearView`), `StretchRect` (copy, or a scaling blit), `ColorFill`,
`UpdateSurface`/`UpdateTexture`, `GetRenderTargetData`, queries (event,
occlusion, timestamps), state blocks (recorded and captured), and D3D9's split
public/private reference counts. D3D9 behaviours D3D11 dropped are emulated:
the half-pixel offset of pixel centres, alpha test.

**Fixed function (`d3d9_ff.cpp`).** Generated per state: transform, lighting
(directional, point and spot lights, material sources, specular), vertex and
table fog, texture coordinate generation and texture matrices (with D3D9's
padding rule), pre-transformed vertices, and the texture-stage combiner with
every operation except bump mapping. It writes the same varying slots as
translated shaders, so the two mix.

**Presentation (`uwp/Kiosk/Native/D3D9Bridge.cs`).** The app hooks the
packaged DLL at startup; each `Present` hands the back buffer texture to
`GraphicsBridge.HandFrame`, which mirrors it exactly as a fake swap chain's.
The layer's log lines join GraphicsBridge's notes.

**Tests.** `test_dxso` renders every translated shader against the same HLSL
compiled straight to SM5 under WARP — pixel-identical (worst difference
0.000007). `test_d3d9` drives the D3D9 API as a game would and reads the
results back: clears, programmable and fixed-function draws, texel-exact
sampling at D3D9 pixel centres (both through shaders and through the classic
pre-transformed sprite), alpha test, blending, depth, fans, indexed draws,
`StretchRect`, state blocks, lighting, fog, and reference counting down to a
released device.

### Not yet

  import and COM-vtable thunks, with lock memory handed out from the guest's
  address space (`NativraD3D9SetAllocator` is the hook for it).
- Volume textures, MSAA, bump-mapping stage ops, ps_1_x, hardware shadow-map

- Varying bandwidth: every draw carries all 30 slots; pairing-aware trimming
